## Defects found

### DEFECT 6 (medium) — router branch-4 mis-fires on empty staged scaffolding

The router's documented trigger for the review-staged branch is *"`.vibe-lingual/localize/staged/` is non-empty."* In the real app that directory contained **empty scaffolding directories** left by a prior run:

```
staged/staged-manifest.json   → {"schemaVersion": 1, "files": {}}
staged/messages/en/           → 0 entries
staged/src/components/        → 0 entries
```

A directory-emptiness test is therefore true while **zero rewrites are actually staged**. The router routed to branch 4 and reported "staged rewrites pending" to the user; the error was only caught by reading `staged-manifest.json` directly and finding `files: {}`.

**Fix:** branch 4's trigger must be `Object.keys(staged-manifest.json.files).length > 0`, not directory contents. Empty scaffolding dirs should either not be created, or be pruned when a batch stages nothing.

**Why it matters:** it sends the user to a review branch with nothing to review, and the banner asserts pending work that does not exist. First impression of the router on a real repo was a false statement.

### DEFECT 7 (high) — no staleness signal on the cached inventory; stale state produces a confident false negative

`localize --dry-run` consumed an `inventory.json` captured **2026-06-21, four weeks stale**, and reported *30 files, 0 written, all `skipped-no-change`*. Read plainly that says "extraction is complete." It was measured against an outdated file set: a fresh `scan` immediately after found **358 sites** (the stale inventory held 594), across a materially different file list, and files touched since the capture were absent from the old inventory entirely.

Nothing in the router, the localize preamble, or the dry-run banner warned that the inventory predated the source.

Compounding it: **`inventory.json` carries no timestamp at all.** Top-level keys are `schemaVersion, app, existingI18n, sites, countsByKind, componentsByDensity`, and the inventory schema defines no `capturedAt`/`generatedAt`. Staleness is currently *undetectable* by the plugin, not merely unchecked.

**Fix:** (a) stamp `capturedAt` into `inventory.json` and add it to the schema; (b) have `localize` and the router compare it against the newest source mtime (or an age threshold) and warn — ideally refuse to present a "nothing to do" result from an inventory older than the newest tracked source file. A stale-state false negative is the worst failure mode for this tool: it tells the user the work is done.

### DEFECT 8 (medium-high, honesty seam) — the SKILL documents a `translate` phase the engine does not implement

`engine/cli.mjs --help` exposes exactly: `scan`, `audit`, `extract`, `wire`, `parity`, `detect`. There is **no `translate` subcommand.**

Yet the arc is stated everywhere as *extract → wire → translate → wire-to-locale → guard*; the localize SKILL has a §6 "Translate (draft the catalogs)"; and `--phase <name>` documents `translate` as an accepted value with no engine behind it. In practice translation is an agent + app-LLM step (or keys marked `TODO: translate`).

This surfaced concretely: the user's stated reason for wanting the pipeline was *"I don't know Spanish or Japanese well enough to hand-pass them"* — i.e. they expected the plugin to **produce reviewed-quality translations**. It cannot; it produces an LLM pass wearing the plugin's clothes, with the same review problem the user was trying to escape.

**Fix:** either implement `translate` as a real engine command, or make the SKILL + README explicit that translate is agent-driven, that `--phase translate` has no engine backing, and that catalog *quality* is out of scope. The plugin's honest value is the plumbing (extract/wire/parity/guard), which is genuinely strong — the seam should say so.

## Observation (not a plugin defect) — the localize SKILL did not load via the Skill tool

Two `Skill(vibe-lingual:localize)` invocations returned only a launch line and no SKILL body; a third reported *"already loaded above; instructions unchanged."* The instructions were never delivered. Worked around by reading `skills/localize/SKILL.md` from the plugin cache directly.

Likely a harness/plugin-loader issue rather than a Vibe-Lingual defect, but recorded for repro: `router` and `guide` both loaded normally in the same session; only `localize` (the one invoked with an argument, `--dry-run`) failed to deliver.

## What the run told us about the app (worth keeping)

The remaining 337 included sites are **not app chrome** — the chrome is extracted. They concentrate in content that should *not* be machine-translated:

| File | Sites |
|---|---|
| `src/app/privacy/page.tsx` | 60 |
| `src/app/terms/page.tsx` | 34 |
| `src/app/billing/page.tsx` | 33 |
| `src/app/learn/[slug]/page.tsx` | 20 |
| `src/app/learn/page.tsx` | 16 |
| `src/app/learn/tarot/[slug]/page.tsx` | 15 |
| `src/components/Oneirocriton.tsx` | 15 |

Legal text (privacy/terms) is a liability surface, and `/learn/*` is the app's organic-search asset where translation is a content-strategy decision (hreflang, duplicate content, separate URLs) rather than a codemod. **A localization tool reaching "nothing left but legal and SEO content" is a legitimate stopping point**, and the plugin arguably should say so rather than continuing to offer translate. Worth considering a `scan` block-5 heuristic that flags legal/marketing routes as "not codemod work."
